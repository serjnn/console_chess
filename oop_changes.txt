How the OOP Architecture Has Changed

  #### 1. Elimination of Global Static State (Decoupling)

  • Before: Game parameters (such as  moveCount  and  moveColor ) and board validation flags (like king movements or whether a pawn made a peaceful move) were stored in  static  fields. This temporal
  coupling made it impossible to instantiate multiple games, made unit testing difficult, and caused hidden side-effects during turn validations.
  • After: State is now cleanly encapsulated inside instances. Game.java maintains instance variables for the turn state, while pieces maintain their own historical movement state (via the  hasMoved
  field).

  #### 2. Encapsulation of Behavior and State (Domain Integrity)

  • Before: Domain objects like Piece.java and Coordinates.java were dumb data containers. Piece classes were heavily dependent on global managers modifying static state flags.
  • After:
      • Each piece type encapsulates its movement rules within  isMoveValidForThisType .
      • Coordinates.java now exposes domain logic helpers like  getFileDistance ,  getRankDistance , and  isOutOfBounds . This allows pieces to express move rules in terms of coordinate distance and spatial
      relationships, adhering to the Information Expert design pattern.


  #### 3. Separation of Concerns (Stateless Services & Models)

  • Before: Board.java, managers, and Game.java had blurred boundaries, mixing state tracking, coordinate parsing, movement simulation, and rules checking.
  • After:
      • Board.java acts as the board model representation ( Map<Coordinates, Piece> ), exposing methods for simulating and committing moves.
      • MoveValidator.java serves as a stateless utility service that validates move correctness (checking boundaries, piece ownership, target squares, castling, and pawn actions) without mutating state.
      • Game.java focuses strictly on CLI workflow coordination.


  #### 4. Type-Safe Exception-Driven Domain Control Flow

  • Before: The application misused system exceptions like  ArithmeticException ,  NullPointerException , and general  RuntimeException  to handle ordinary chess rule violations (e.g., trying to capture your
  own piece).
  • After: The introduction of ChessException.java ensures all chess validation errors are type-safe and self-documenting, preventing actual developer programming bugs from being accidentally swallowed.
